# Analysis guidelines for a SQL query

## Goal

Given an AST generated by the parser, we want to do the following things:
1. Create a scope representation of the AST. This can be another tree like data structure, or a traversal/visitor.
2. Use this scope representation to qualify the AST.

## Qualification guidelines

### What is a scope?
A scope is the query (or query block) in which names are resolved. New scopes are created when:
1. At the beginning of the SQL statement i.e. the root scope.
2. Inside paranthesised/nested queries.
3. In set operation (UNION, EXCEPT, INTERSECT) branches. Each branch has its own scope.
### What is qualification?

For each column identifier being used in the query, let's say in the format of `a.b`, do the following things.

1. Check if a the source `a` is available in the scope. By availability, I mean this:
    - The source `a` needs to be "pulled in" into the current scope via a FROM clause.
    - What follows a FROM clause can be many things: a base table, a derived table, a CTE, a UDTF, etc.
2. Check if the column `b` is available in the source `a`.

### Source availability

What determines if a source exists/visible in a scope?

**Subquery**: A subquery is a parenthesized query that appears in expressions or predicates (e.g. WHERE, SELECT list, HAVING, ON), not as a FROM item.

**Derived Table**: A paranthesised query that appears as a FROM clause. In short, a paranthesised query that IS a source.

The below examples use subqueries in the WHERE clause, but the following also apply to subqueries in the SELECT, HAVING, ON etc. clauses.

1. Directly pulled in from a FROM clause. Example:
    ```
    SELECT table1.a FROM table1 <--- table1 directly available to the rest of the query.
    ```
2. If the current scope is a subquery. There exists a mechanism called *Correlation*, that makes the sources in the parent scopes visible to the current scope.
    ```
    SELECT d.department_id, d.department_name
    FROM departments d
    WHERE NOT EXISTS (
        SELECT 1
        FROM employees e
        WHERE e.department_id = d.department_id <---- department d visible 
    );
    ```
    If the current scope is a subquery, it is allowed to see its parents sources too.
3. Transitive visiblity: If subquery can see its parents sources, and the parent itself can see its parents sources, then by transitivity, the subquery can see its grandparent's sources
    ```
    SELECT t1.id AS t1_id
    FROM t1
    WHERE t1.id IN (
    SELECT t2.t1_id
    FROM t2
    WHERE t2.id IN (
        SELECT t3.t2_id
        FROM t3
        WHERE t3.id = 100
        AND t1.id = t2.t1_id   /* t1 = grandparent, t2 = parent */
    )
    );
    ```
4. LATERAL derived tables. Under normal circumstances, a derived table cannot reference sources outside of its scope. In standard SQL, a non-LATERAL derived table is evaluated independently and has no access to the outer query’s FROM.
    ```
    SELECT
        salesperson.name,
        max_sale.amount,
        max_sale_customer.customer_name
    FROM
        salesperson,
        (
            SELECT MAX(amount) AS amount
            FROM all_sales
            WHERE all_sales.salesperson_id = salesperson.id <--- No salesperson found
        )
    ```
    Specifying a LATERAL derived table, exposes the parents sources to the current scope(the derived table).
    ```
    SELECT
        salesperson.name,
        max_sale.amount,
        max_sale_customer.customer_name
    FROM
        salesperson,
        LATERAL (
            SELECT MAX(amount) AS amount
            FROM all_sales
            WHERE all_sales.salesperson_id = salesperson.id <--- Visible
        )
    ```
5. Transitive LATERAL: Similar to point 3.
    ```
    SELECT t1.id AS t1_id, t2.id AS t2_id
    FROM t1 
    CROSS JOIN LATERAL (
        SELECT t2.id, t2.t1_id
        FROM t2
        CROSS JOIN LATERAL (
            SELECT t3.id
            FROM t3
            WHERE t3.t2_id = t2.id
            AND t1.id = t2.t1_id   /* t1 = grandparent, t2 = parent */
        ) t3
        WHERE t2.t1_id = t1.id
    ) t2;
    ```
    Not specifying `t2` as LATERAL would "sever" the connection between the main query and `t2`, and `t1` would not be visible anymore to `t3`.
6. FROM order for LATERAL: A LATERAL derived table is only allowed to see sources that precede it in the from order. This is to prevent invalid forward/circular references.
7. CTEs: A CTE does not act as source until it is pulled in via a FROM clause. Until then, it is merely a table definition.
    - CTEs are valid in the scope they are defined, and also in all the child scopes of the current scope.
    - A recursive CTE would be valid in its OWN nested scope.

3. HAVING legality is *not* a name-resolution concern. Standard SQL requires that every column reference in HAVING is either (a) a grouping column or (b) wrapped in an aggregate. Name resolution only asks "does this column exist in a visible source?" - so all of the following resolve identically here:
    ```
    HAVING id > 0           -- illegal in standard SQL / MySQL ONLY_FULL_GROUP_BY, we accept
    HAVING MAX(id) > 0      -- legal (aggregated), we accept
    HAVING t2_id > 0        -- legal (grouping column), we accept
    ```
    MySQL with `ONLY_FULL_GROUP_BY` disabled will even silently pick an arbitrary row's value for the bare form. Engines reject (or don't) this at validation time, not at resolution time. From a lineage standpoint, recording the column dep is the correct answer regardless of legality - the query *does* depend on that column. Legality would be a separate pass over the resolved tree (using `group_by_columns` + aggregate-aware traversal).
4. The same applies to GROUP BY: we don't model alias references (`GROUP BY total` where `total` is a SELECT alias) or positional refs (`GROUP BY 1`). Both forms would currently fail to resolve.
